# ADR-0002 — Reference management: bib-authoritative, Zotero as picker, no word-processor plugin

- **Status:** accepted
- **Date:** 2026-08-24
- **Deciders:** Alex (owner); drafted with the research-engineer agent

## Context

`dream-dynamics.md` cited 49 hand-numbered references until 2026-08-24, when the citation layer
was converted to pandoc citekeys (`[@beradt1968third]`) with the list generated by citeproc from
`70-papers/academic/references-seed.bib`. That fixed two defects a numbered style cannot tolerate:
the printed numbers were not in order of first appearance, and six entries bundled two distinct
works under one number, which CSL cannot represent.

Preparing the Word submission copy exposed the remaining question — *which tool owns the
bibliography* — through two failures.

Zotero's word-processor plugin refused to edit the references in the generated `.docx`, reporting
that citations had to be added first. That is the correct response rather than a misconfiguration:
the plugin stores each citation as a Word field carrying its own item metadata and only edits
fields it created, whereas pandoc emits finished text. Nothing about the setup changes this; the
two tools both want to own the bibliography.

Underneath that sat a second fact, found by checking `references-seed.bib` against
`zotero.sqlite`: **1 of 51 DOIs was in the Zotero library at all.** The bibliography had been
assembled from a curated DOI table resolved through CrossRef and had never passed through Zotero,
so no Zotero-based tool — in Word or in Obsidian — had anything to work with.

## Decisions

1. **`references-seed.bib` is authoritative for reference metadata.** It is built and DOI-verified
   by `scripts/build_references_bib.py` against the archived numbered list
   (`references-numbered-archive.md`), and carries the brace protection that stops CSL styles
   down-casing proper nouns (`XLM-T`, `Twitter`, `Siamese`, `Lord`). Pandoc reads it directly.
2. **Zotero is a citation picker, not a source of truth.** The 59 works were imported into the
   library so a picker can offer them, tagged `dream-dynamics` for identification. Sync is
   one-way, bib → Zotero, via `scripts/zotero_sync.py`; nothing is written back. That keeps the
   DOI verification and the proper-noun protection, which are code, from depending on the state of
   a GUI library of 8,980 items.
3. **Citations are edited in the markdown, not in Word.** The `.docx` is a disposable build
   artifact from `scripts/build_manuscript.py`. The Zotero word-processor plugin is not used.
4. **Two Obsidian plugins, with separate jobs** (`scripts/install_obsidian_zotero.sh`).
   *Zotero Integration* inserts citations, configured with pandoc format and brackets so it writes
   `[@key]` — the manuscript's own form; it calls Better BibTeX's cite-as-you-write endpoint rather
   than Zotero internals. *Pandoc Reference List* displays them, since Obsidian cannot format
   citations itself: `[@key]` stays literal and the `::: {#refs}` block stays empty until pandoc
   runs. It is pointed at `references-seed.bib` with `pullFromZotero` off, keeping decision 1 in
   force in the editor as well, and at the vendored `nature-brackets.csl` with `cslLang: en-GB` to
   match the locale the style declares — so the sidebar renders what the build renders.
5. **Imported citekeys are pinned, not computed.** This profile's BBT key formula is
   `auth.lower + shorttitle(3, 3) + year`, which would have named Beradt `beradtThirdReichDreams1968`
   against the manuscript's `beradt1968third` and broken all 59 citations at once. BBT's
   `importCitationKey` preference (default true, verified in the installed 9.0.58) overrides the
   formula with the key from the imported file, and the keys landed in Zotero's native
   `citationKey` field — a stored value, not a formula cache, so a key refresh cannot rewrite them.
   Verified: 59 of 59 resolve and match the bib exactly, no duplicates.

## Consequences

- One command rebuilds the whole citation layer, and the manuscript stays the source of truth —
  the same file-over-app property the data pipeline has.
- Adding a reference means adding it to the identifier table and rebuilding, then re-running
  `zotero_sync.py --import` so the picker can see it. `zotero_sync.py` with no arguments verifies
  that every cited key still resolves and is the check to run before a submission build.
- Metadata corrected *in Zotero* will not reach the manuscript. This is deliberate, and the cost
  of the decision: fixes belong in the identifier table.
- **The manuscript declares no `bibliography` or `csl` in its YAML**; `build_manuscript.py` passes
  both as arguments. This is forced by Pandoc Reference List, which resolves a frontmatter
  `bibliography` against the *vault root* rather than the note and — in `getReferenceList`, outside
  any try/catch, while registering a file watcher — throws when the path does not resolve. The
  throw aborts the whole render and the sidebar reports "No citations found in the current
  document", which reads as a broken bibliography rather than a path error. A note with no such
  frontmatter takes the plugin's own configured paths and renders correctly. Rewriting the
  frontmatter as vault-relative would also have satisfied the plugin, but only for a build run from
  the repository root, and its `csl` would still have failed: that path is checked against the
  process working directory with no vault fallback, and for any note carrying frontmatter the
  plugin's style fallback is `cslStyleURL` — defaulting to APA — so the sidebar would have rendered
  in the wrong style rather than failing visibly. Passing both as arguments also makes the build
  independent of the working directory, which the relative frontmatter was not.
- The cost is that a bare `pandoc dream-dynamics.md --citeproc` no longer resolves citations. It
  fails loudly — `[?]` markers and a Citeproc warning per key — rather than silently, and
  `build_manuscript.py` is the documented entry point.
- Zotero Integration last released 3.2.1 in August 2024 and its repository has moved to
  `community-archive`. It depends on Better BibTeX's endpoint rather than Zotero internals, so it
  is not expected to break with Zotero updates, but the maintained alternative is ZotLit
  (`aidenlx/zotlit`) and switching would not disturb decisions 1–3.
- The vendored plugin bundle (~1 MB of minified JS) is gitignored; the pinned version and its
  sha256 checksums are the tracked artifact, verified before the files reach the vault.

## Follow-ups

- If a journal requires a Word-native bibliography, the supported bridge from static citation text
  to live Zotero fields is the *RTF/ODF Scan for Zotero* add-on, which needs ODT output and the
  Scannable Cite style. Not built, because no target journal has asked for it.
